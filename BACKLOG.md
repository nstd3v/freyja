# Backlog — findings from repository analysis

The current plan detects changes, but a rebuild is not necessarily built from the dependency version that was resolved. `SKIP` is a state-fingerprint decision, not proof that the expected local image exists. Keep these limitations explicit until the corresponding build and state transitions are tested.

## Build correctness

- [FB-001] **Deliver the resolved OCI digest to the build.** Pass the dependency map from the *same plan* to the builder, without resolving it again. Define and validate a mapping from each OCI dependency to a Dockerfile build argument; pass a digest-pinned image reference so `FROM` uses the resolved digest. Test the actual `podman` argv with a fake executable, including changed digests, invalid mappings, and absence of credentials. Update the OCI example only after the mapping works. Do not claim digest-pinned builds before this is verified.
- [FB-006] **Deliver resolved APK versions to the build.** The resolver currently uses version/checksum to decide whether to rebuild, while `apk add` can install a different version. Define the Dockerfile/build-argument contract, pass the version from the same plan, and test the command input and a changed-version rebuild. Keep the documented limitation until verified.
- [FB-017] **Deliver resolved ALT RPM and Debian package identities to builds, or describe them strictly as rebuild triggers.** Both resolvers can detect a package change without making the package installed by the Dockerfile match the resolved candidate. Define supported version-pinning contracts for each package manager, pass the plan's resolved identity into the build, and test the resulting build input; if pinning is not supported, retain explicit trigger-only semantics rather than claiming reproducibility. Depend on the plan-to-builder interface in FB-001.
- [FB-003] **Honor or reject declared tags and architectures.** `tags` and `arches` affect the target fingerprint but not the Podman command. Apply supported values to the actual build invocation and test its argv, or reject unsupported values before recording a successful build.

## Output and state integrity

- [FB-015] **Check that a skipped output still exists.** A matching fingerprint can produce `SKIP` after the locally tagged image has been removed. Define how to identify/inspect the expected local output before skipping; rebuild when it is absent or no longer matches, and test removal or replacement between builds. Distinguish image identity checks from dependency resolution.
- [FB-008] **Reject colliding effective image tags.** Two targets with the same `image` can both record success although the second replaces the first target's output. Validate collisions across primary images and any tags introduced by FB-003 before building; test that a conflicting spec cannot produce a misleading `SKIP`.
- [FB-009] **Include build-relevant file modes in context fingerprints.** Changing a copied file from `0644` to `0755` can leave the plan at `SKIP`. Hash relevant mode bits and test a mode-only change without treating mtime as a build input.
- [FB-010] **Create state temporary files safely.** `State::save` uses a predictable `<state>.tmp` path and can follow a pre-existing symlink. Use a unique, exclusively created temporary file in the state directory followed by atomic replacement. Test symlink safety and cleanup on failure.
- [FB-011] **Coordinate concurrent state writers.** Separate builds can load the same initial state and overwrite each other's records. Lock the state transaction or detect and merge conflicts; test simultaneous builds of different targets so both records survive without a false success report. Coordinate this with FB-010.
- [FB-016] **Keep resolver caches outside build contexts.** A cache refresh inside a context changes the context fingerprint, potentially after the plan calculated it, and causes a subsequent rebuild unrelated to source inputs. Reject cache paths inside any context or deliberately exclude them with a sound builder-input contract; test a context containing `.freyja/cache`, including refresh between plan and build. State paths are already checked separately.

## Resolver trust, freshness, and resource bounds

- [FB-007] **Verify APKINDEX authenticity.** HTTPS transport alone does not authenticate Alpine's index as signed repository metadata. Define trusted keys, verify the archive before caching or resolving, and test tampering and key rotation.
- [FB-012] **Validate ALT RPM indexes before caching.** Downloaded compressed bytes are currently cached before decompression and parsing; malformed bytes can poison a fresh cache entry. Validate first, then replace the cache atomically; test that a bad download preserves a previous valid entry.
- [FB-013] **Expire in-memory APK and ALT RPM indexes.** The in-memory maps bypass disk TTL checks after the first lookup. Track freshness or revalidate on later lookups, and test an expiry transition without a live network.
- [FB-014] **Bound ALT RPM FTP work.** Apply an overall deadline to connection, login, transfer, and completion, plus compressed-download and expanded-XZ limits. Test stalled streams and oversized payloads with bounded resource use and clear errors.
